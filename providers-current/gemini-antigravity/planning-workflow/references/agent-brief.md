# AFK agent brief

Read only when a ready issue needs the durable contract an AFK agent will execute.

1. Make the brief the authority, not a pointer to issue discussion or conversation memory.
2. State category, current behavior, desired behavior (including errors/edge cases), key durable interfaces or configuration shapes, testable acceptance criteria, and non-goals.
3. Describe behavior rather than procedures. Do not freeze stale file paths or line numbers; name an interface or contract only when it changes the work boundary.
4. Keep every criterion independently verifiable and every scope exclusion explicit. Explain why a ready-for-human issue cannot safely become AFK.

Post or save the brief only through the configured workflow and after any required maintainer preview.
