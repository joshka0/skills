# PRD

Read only when current context needs a one-shot product requirements document.

1. Use current context and relevant repository/domain documentation; do not run a broad interview. Ask only about a missing decision that materially changes the product outcome or tracker publication.
2. State the problem and user outcome, solution, distinct user stories and edge cases, implementation decisions, testing decisions, out-of-scope boundary, and unresolved notes.
3. Use project glossary terms and surface an ADR conflict instead of silently overriding it.
4. Keep the artifact behavioral and durable. Avoid exact paths or snippets unless a prototype encodes an approved decision more precisely than prose.

Publish only through the configured tracker workflow and only when the user requested publication.
