# Issue triage

Read only when an incoming issue needs a configured classification, state recommendation, or public tracker outcome.

1. Read the full issue, prior comments, configured labels, reporter updates, relevant domain/ADR context, and matching durable rejection records. Do not re-ask resolved questions.
2. Assign one configured category and one configured state role; flag conflicting states for the maintainer instead of guessing a transition.
3. Recommend with evidence, then wait for direction before public mutation. Attempt a bug reproduction before requesting broad clarification.
4. Use an AFK brief only after the issue is ready. If the user asks to prepare it, continue with the `issues` mode after the triage outcome is approved.
5. After a maintainer approves rejecting an enhancement, record one concept—not one issue—at `.out-of-scope/<concept>.md` or the repository's configured equivalent. Include the decision, durable rationale, and linked prior requests; temporary capacity deferrals do not belong there.
6. On a later concept match, surface the prior decision for confirmation rather than silently closing the request. When reconsidered, supersede or update the record according to repository convention; do not erase decision history by default.
7. Preview public text and any durable record update unless supplied by the maintainer. Every AI-generated triage comment starts with:

> *This was generated by AI during triage.*

Configured tracker documentation, not this skill, supplies current CLI/API syntax.
